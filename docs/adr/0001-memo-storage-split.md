# 0001. メモの本文は S3、見出しは PostgreSQL、読み出しは Redis 経由とし、ID は公開時刻から作る

- Status: Accepted
- Date: 2026-09-13

## Context

`packages/Samples/` は AGENTS.md の配置規則を示す参照実装で、Compose に用意した RustFS(S3 互換)、PostgreSQL、Redis の 3 つを一つの機能で使って見せる役目を持つ。同時に、このリポジトリは数年単位の運用を前提にするので、参照実装であっても永続化した形式は互換境界として扱う。

メモは見出し、本文、公開日時を持ち、一覧は公開日時の降順で見出しだけを出す。本文は長くなりうるが一覧には要らない。

## Decision

本文を含むメモ全体を S3 の `memos/<id>.json` に JSON で保存し、一覧に必要な `id`、`title`、`published_at` だけを PostgreSQL の `memos` テーブル(`database/schema.sql`)に記録する。表示は Redis のキャッシュ(`samples.memo.<id>`)を先に見て、なければ S3 から読んでキャッシュに入れる。3 つの保存先は `Domain/` の port(`MemoRepository`、`MemoIndex`、`MemoCache`)で分け、UseCase が順に呼ぶ。

ID は公開時刻をマイクロ秒まで含む `YYYYMMDD-HHMMSS-uuuuuu` とする(`MemoId::PATTERN`)。文字列順が時刻順になるので、索引の並びは主キーの降順で済み、URL とコマンド引数にそのまま使える。S3 の JSON でも `published_at` はマイクロ秒を保持する。ID と DB 行がマイクロ秒を持つのに JSON だけがミリ秒に丸まると、読み戻したメモの公開時刻が書いたものとずれる(実際に一度起きた)。

## Alternatives

PostgreSQL に本文も置く。保存先が 1 つになり最も単純だが、S3 を使う例がなくなり、参照実装の役目を果たせない。業務パッケージでは、本文が大きくならず一覧と同じ整合性が必要なら、こちらを選んでよい。

S3 だけに置き、一覧は S3 の ListObjects で作る。DB が不要になるが、見出しを得るには各オブジェクトを読む必要があり、件数に比例して遅くなる。索引を別に持つ設計を示すという目的にも合わない。

ID を ULID や UUIDv7 にする。時刻順は保てるが、人が読んで公開時刻を判別できず、コマンドラインで打つには長い。参照実装では読みやすさを優先した。衝突耐性が要る業務パッケージでは UUIDv7 を選ぶこと。

## Consequences

書き込みが 3 か所に分かれるので、公開・編集・削除は UseCase が S3 → PostgreSQL → Redis の順で呼び、途中で失敗すると不整合が残る。参照実装ではこれを許容し、補償処理は持たない。業務パッケージで同じ構成を採るなら、S3 を正とし索引とキャッシュは再構築できるものと位置づけるか、トランザクション境界を DB 側に寄せる判断が要る。

キャッシュにしか残っていないメモが起こりうる(S3 から消えた後も TTL まで表示できる)。編集と削除は S3 を正として存在を判定する。

同一マイクロ秒に 2 件公開すると ID が衝突する。参照実装の負荷では起きないものとして受け入れる。

JSON の形式、テーブルの列、キャッシュのキーを変えるときは AGENTS.md「長期運用で効いてくること」に従い、旧形式の読み出しか移行を同じ変更に含める。
